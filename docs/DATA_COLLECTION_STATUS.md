법원경매 공급원이 연결되면 다음 항목을 검증한 자료만 게시합니다.

- 사건번호와 물건번호의 고유성
- 소재지, 용도, 법원, 매각기일, 감정가, 최저매각가격
- 매각물건명세서, 현황조사보고서, 감정평가서 원문 확인 경로
- 개인정보 및 주민등록번호 패턴 미포함
- 검수 승인 표시와 출처 정보
- 목록 건수, 상세 파일 건수, 콘텐츠 해시 일치

## 5. 상태값 해석 기준

| 상태 | 의미 | 화면 표시 원칙 |
| --- | --- | --- |
| `ready` | 검증된 자료가 현재 배포 매니페스트와 일치 | 정상 및 실제 건수 표시 |
| `empty` | 검증된 배포 자료가 0건 | 원인과 공급원 상태를 함께 표시 |
| `unconfigured` | 필요한 공급원 또는 인증 설정이 없음 | “공급원 미연결”로 표시, 완료로 표현 금지 |
| `failed` / `error` | 최근 실행 실패 | 실패 시각과 “이전 정상 자료 유지” 표시 |
| `unknown` | 상태 JSON을 읽지 못했거나 해석 불가 | 0으로 바꾸지 않고 “확인 불가” 표시 |

## 6. 건수와 검증 계산 기준

| 지표 | 계산 기준 |
| --- | --- |
| 입찰건 | 현재 배포 매니페스트의 `itemCount` |
| 고유 물건 | 물건 관리번호 중복을 제외한 `distinctProperties` |
| 사진 물건 | 배포 매니페스트의 `photoProperties` 우선. 누락 시 수집 시각·건수·명시된 snapshotId가 같은 정상 수집 상태에서만 보완 |
| 사진 총합 | 모든 데이터셋의 사진 수가 확인된 경우에만 합산. 미측정은 0건으로 추정하지 않으며, 명시적으로 빈 배포 목록만 0건 |
| 검증률 | 현재 배포 스냅샷과 최근 정상 수집 스냅샷이 일치할 때 `itemCount / expectedCount × 100` |
| 최근 정상 수집 | 배포 중인 매니페스트의 `collectedAt`과 상태 파일의 `lastSuccessAt`이 일치하는 시각 |
| 최근 시도 | 상태 파일의 `attemptedAt` |
| 수집 완료 | 검증 성공만이 아니라 검토 PR 병합과 Pages 배포 성공까지 확인된 상태 |

수집 시도의 건수가 현재 배포 건수와 다르면 시도 건수를 운영 건수로 표시하지 않습니다. 알 수 없는 값은 0이 아닌 `—` 또는 “확인 불가”로 표시합니다.

## 8. 운영 갱신 원칙

- 데이터가 실제로 수집된 경우 `data-status.html`에서 배포 건수, 검증률, 정상 수집 시각, 최근 시도 결과를 표시합니다.
- 법원경매 `AUCTION_FEED_URL`이 연결되지 않은 동안은 법원 수집을 완료 또는 정상으로 표현하지 않습니다.
- 수집 실행, 검토 PR, Pages 배포 상태를 서로 분리해 표시합니다.
- 예시 데이터, 사용자의 직접 등록 사건, 관심 물건, 메모와 체크리스트는 공개 수집 건수에서 제외합니다.
- 수집 범위나 집계 기준이 변경되면 이 문서와 `data-status.html`을 함께 갱신합니다.

## 9. 법원 상세 화면 수준의 정보 제공 가능성

결론은 **상세정보를 표시하는 스키마와 화면은 구현되어 있으며, 실제 사진·상세자료의 추가 수집이 필요한 상태**입니다. 첨부된 법원 화면의 사진, 사건일자, 기일내역, 목록내역, 감정평가 요약, 공개문서 링크에 대응하는 필드가 `scripts/collect-auctions.mjs`와 `app.js`에 이미 있습니다. 법원 공급원은 미연결이며, 현재 온비드 수집기는 목록 필드와 사진 보강만 매핑합니다.

2026-10-22 저장소의 `data/auctions.json`과 `data/onbid/auctions.json`을 전수 확인했습니다. 법원은 0건이고 온비드 7,512건 중 `imageUrls`, `caseDetails`, `schedules`, `propertyLots`, `appraisalSummary`, `documents`, `tenancySummary`를 보유한 레코드는 각각 0건입니다. 화면·스키마 지원을 실제 자료 수집 완료로 해석하면 안 됩니다.

[사법정보공유포털의 OpenAPI 안내](https://openapi.scourt.go.kr/kgso202m01.do)는 연계 API 사용에 관해 법원행정처 API 담당자에게 별도 문의하도록 안내하고 있으며, 일반 오픈 API는 추후 업데이트 예정이라고 안내합니다. 경매 상세·사진을 제공받을 수 있는지, 해당 서비스에서 재이용할 수 있는지는 별도 확인이 필요합니다.

| 목록내역 상세 | `propertyLots` 목록번호·구분·소재지·면적·지분·상세 지원 | 없음 | 물건 내 토지·건물 목록별 원본 자료 수집·매핑 |
| 감정평가 요약 | `appraisalSummary` 평가일·위치·교통·주변환경·구조·설비·이용상태 등 지원 | 없음 | 공식 평가정보 수집·매핑 |
| 임차관계·점유 상세 | `tenancySummary` 조사상태·주체 수·비식별 요약 지원 | 없음 | 개인정보를 제외한 확인된 요약 자료 필요 |
| 현황조사서·감정평가서·매각물건명세서 | `documents` 공개 여부·공시일·원문 URL 표시 지원 | 실제 문서 URL·PDF 없음 | 개별 물건에 대응하는 공개문서 주소·공시일 수집. PDF 자체 수집·보관은 별도 |

### 9.2 사진 수집 점검 결과

경매한눈의 정규화 스키마와 화면은 `imageUrls`를 최대 8개까지 받을 수 있습니다. 온비드 수집기 역시 물건목록의 물건관리번호로 공식 상세 API를 조회하고 사진 URL을 보강하는 코드가 구현되어 있습니다.

하지만 현재 운영 데이터는 다음 상태입니다.

| 점검 항목 | 결과 |
| --- | --- |
| 온비드 배포 입찰건 | 7,512건 |
| 온비드 고유 물건 | 4,466건 |
| `imageUrls`가 있는 현재 배포 레코드 | 0건 |
| `manifest.photoProperties` | 없음 |
| `collection-status.photoProperties` | 없음 |
| 운영 워크플로의 `ONBID_IMAGE_ENRICH_LIMIT` | 기본 80건으로 구현, 다음 수집 실행부터 적용 |
| `npm run collect:onbid` 실행 기본 사진 보강 한도 | 환경변수 미지정 시 80건. 수집 함수 자체의 기본 인수는 0건 |
| 목록·상세 화면 표시 방식 | 목록은 첫 사진, 상세는 최대 8장 이전·다음·썸네일 지원 |
| 사진 없는 물건·실패 기록 | 현재 장기 이력·재시도 간격 저장 없음. 앞쪽 물건을 반복 조회할 수 있어 보완 필요 |

따라서 **사진 포함 데이터 수집이 추가로 필요합니다.** 온비드는 현재 구현된 사진 보강 기능을 실행하고 수집 결과를 검수·배포해야 합니다. 기본 80개 물건 조회는 현재 고유 물건 4,466개의 약 1.8%이며, 사진이 없거나 조회에 실패할 수 있으므로 실제 사진 확보율과 같지 않습니다. 법원 사진은 사건 상세 데이터와 함께 이용 가능한 공급 경로를 먼저 확보해야 합니다.

온비드의 [부동산 물건상세 API](https://www.data.go.kr/data/15157247/openapi.do)는 사진·면적 상세·감정평가정보의 확장 경로이며, [물건상세 입찰정보 API](https://www.data.go.kr/data/15157251/openapi.do)는 회차별 입찰정보, [공매공고 API](https://www.data.go.kr/data/15157218/openapi.do)는 공고와 첨부파일의 확장 경로입니다. 현재 사진 추출 외 필드가 위 스키마로 자동 매핑되는 것은 아니므로 각각 수집·매핑·연결 정확성 검증이 필요합니다. 온비드 API는 법원 사건 자료의 공급원을 대신하지 않습니다.

### 9.3 권장 구현 순서

| 우선순위 | 작업 | 결과 |
| ---: | --- | --- |
| 1 | 온비드 사진 보강 수집 실행·검수·배포 | 기본 80건 설정 구현. 현재 배포본은 사진 0건이므로 실제 보강 실행과 데이터 PR·배포 확인이 남음 |
| 2 | 수집 상태에 `photoProperties`와 사진 보유율 표시 | 구현 완료: 같은 배포 스냅샷의 수치만 사용, 미측정을 0건으로 추정하지 않음 |
| 3 | 상세 화면에 최대 8장 갤러리 구현 | 구현 완료: 목록은 대표 사진 1장, 상세는 이전·다음·썸네일 제공 |
| 4 | 법원행정처 연계 API 또는 재배포 허용 피드 확보 | 외부 승인 필요: 법원 사건·물건·기일 기본 데이터 수집 시작 조건 |
| 5 | 법원 상세 확장 스키마 설계 | 구현 완료: 기일내역, 목록내역, 사건일자, 감정평가 요약, 문서 링크, 비식별 점유요약 지원 |
| 6 | 문서·사진 이용조건 검증 | 출처 표시, 원문 링크, 저장·재배포·핫링크 허용 범위 확인 |
| 7 | 개인정보 제거 및 변경 추적 | 임차관계 등 민감 가능 필드 필터링, 문서 공시·정정 시각 기록 |
| 8 | 사진 보강의 장기 진행 상태·재시도 간격 관리 | 미구현: 사진 없음·조회 실패를 구분해 앞쪽 물건만 반복 조회하는 현상 방지 |

온비드 사진 보강은 API 호출 한도 내에서 점진적으로 실행하며, 이미 확보한 사진은 물건관리번호 기준으로 재사용합니다. 사진 주소 수집 성공, 실제 이미지 표시 성공, 전체 물건 사진 확보는 서로 다른 단계로 점검해야 합니다.
